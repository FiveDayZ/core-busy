# 核心经验值（EXP）与 99 级成长曲线

> 状态：**已实现并通过验证**（v1.22.0，2026-10-09）。本文给出可直接落码的完整口径与等级表。
> 实现文件：`Core/Progression/`（3 个类）+ `App/Services/CoreExpStore.cs`。
> 验证脚本：`.workbuddy/expprobe/`（曲线与口径 77 断言）、`.workbuddy/storeprobe/`（账本往返 36 断言）、
> `.workbuddy/gen_exp_curve.py`（生成与标定）；产出数据：`docs/_exp_curve.json`、`docs/_exp_table.md`。

## 一、为什么 EXP 是这里唯一安全的游戏化货币

健康度已被 README 判定为**合成代理指标**，不是损耗百分比。因此等级**不得**由健康度换算，
也不得使用「剩余寿命 / 磨损百分比 / 预计还能用 N 年」这类文案。

EXP 不同：它是**实测量的时间积分**，等价于"这颗核累计满了多少核·小时"。
它不描述硬件好坏，只描述"它陪你跑了多久"。因此可以安全地拿来做等级。

## 二、EXP 计算口径

单位：**核·分**（core-minute）。1核·小时 = 60 EXP。选核·分是为了让Lv.1→2 的门槛
恰好等于"单核满载 12 分钟"，首日即可感知。

### 2.1 三项来源

| 项 | 公式 | 说明 |
| --- | --- | --- |
| 负荷经验 | `∫(核占用% / 100) dt` | 主项。等价于 `CumulativeLoadTracker` 的核·秒 ÷ 60 |
| 陪伴兜底 | `观测时长 × 0.15` | 仅在核占用处于 **5% ~ 15%** 区间时启用 |
| 计数 | `EXP = max(负荷经验, 陪伴兜底)` | **取max，不相加** |

### 2.2 三个关键设计决定

**(1) 为什么不用"陪伴时长"当主项**
陪伴时长对所有核完全相同 —— 8颗核会同一天升到同一级，等级失去区分度。

**(2) 为什么不用纯负荷经验**
纯负荷奖励把核心压满，等于永久惩罚摸鱼核。轻载核必须有一条不归零的路。

**(3) 为什么是 `max` 而不是相加**
若相加，占用 5%~15% 的核会拿到 `负荷 + 兜底` 的双份，在该区间产生约 2.5 倍套利。
`max` 让两项互为兜底、互不叠加。

### 2.3 边界行为（24 小时单核）

| 核占用 | 负荷 | 兜底 | 实得 | 说明 |
| ---: | ---: | ---: | ---: | --- |
| 0% | 0 | — | **0** | 完全摸鱼，不给任何经验 |
| 3% | 43 | — | **43** | 低于有感知阈值，按负荷（不给兜底） |
| 5% | 72 | 216 | **216** | 兜底生效 |
| 8% | 115 | 216 | **216** | 兜底生效 |
| 15% | 216 | 216 | **216** | 负荷与兜底交汇 |
| 20% | 288 | 216 | **288** | 按负荷 |
| 100% | 1440 | 216 | **1440** | 按负荷 |

常量：`MinLoadPct = 15.0`、`FloorFactor = 0.15`、`PresentFloorPct = 5.0`。

### 2.6 实现期修正：三处口径与代码不一致

以下三点是**实现并跑验证时才发现的**，与上文最初设想不同，以这里为准。

**(1) 兜底必须逐段累加，不是取max**

最初实现写成 `_floor = Math.Max(prevFloor, curFloor)`，理由是"同一段内负荷与兜底不叠加"。
**这是错的**：兜底是**逐 Δt 区间**判定的量，每段 Δt 不同、判定结果也不同，
用`max` 会把此前所有分段的钱丢掉。实测 240 段 × 14%（每段 1 小时）只剩最后一段的 0.9 核·分，
而非 216。

正确口径：**不同段之间各自累加；同一段内负荷与兜底不相加**（由 `max` 承担）。

**(2) 边界容差必须相对化**

`LevelOf` 的容差原取固定 `1e-6`。逐级验证发现**99 级全部失配** —— 阈值本身一旦超过
`1e-6` 量级，容差就反过来把"刚过阈值一点点"的值全判成高一级。

改为**相对容差** `1e-15`（约 4~5 个 ulp）：既吸收 `Math.Log` 的舍入误差
（`C(6)=78.5` 恰在切换点上，差一个 ulp 掉级），又不大到掩盖真实档位。
实现用 `AdjustUp` / `AdjustDown` 两次修正，阈值判定是**含等号**的。

**(3) 倍率必须存满 17 位有效数字**

总量对 `R` 极敏感，截断误差被 `r^(L-1)` 放大：

| 有效位 | `R` | 满级总量误差 |
| ---: | --- | ---: |
| 6 | 1.13479 | **−61.5 核·时** |
| 9 | 1.13479218 | −0.006 核·时 |
| 14 | 1.1347921802052 | +0.000001 核·时 |
| **17** | **1.1347921802051704** | **< 1e-6 核·时** |

定为 `R = 1.1347921802051704`。

### 2.4 物理核归并（必须）

`CumulativeLoadTracker` 按 `Id` 索引，物理核与逻辑线程（`T0`/`T1`）在同一字典里。
EXP **必须按物理核累计**，SMT 线程数只作为展示明细。否则一颗物理核会分裂成两个等级。

### 2.5Δt 口径

一律取**墙钟差**，与 `CumulativeLoadTracker.Accumulate` 完全一致。
采样周期改档、性能模式、切后台被节流，都不得让积分权重失真。

## 三、等级曲线：解析式而非查表

### 3.1 公式

设 `T0 = 12`核·分、`r = 1.134792`、`Lmax = 99`：

```
C(L) = T0 × (r^(L-1) - 1) / (r - 1)          升到Lv L 所需累计 EXP
S    = T0 / (r - 1)
L(c) = 1 + log(1 + c / S) / log(r)           由累计 EXP 反解等级
```

`r` 不是手调的，而是**反解出来的** —— 令 `C(99)/60 = 357,408 核·时`
（满载机 6 年），对 `r` 二分求解，标定误差 0.0000 核·时。

### 3.2 为什么必须用解析式（v2 失败复盘）

最初用 1-2-5 阶梯取整 + 增量查表，两个致命问题：

1. **不单调**：取整后相邻增量大量相等，被迫做单调化修正；
   而修正用的绝对量 `+1` 与阶梯吸附互相锁死，导致总量对 `r` 完全不敏感
   （实测 `r` 从 1.02到 1.15，总和恒为 1.08 亿，二分法永远收敛到边界）。
2. **数量级跳跃**：改成乘法修正后联动恢复，但台阶跨越使 `total(r)` 突跳
   （`r` 1.12→1.14 总量翻 4 倍），「99级 + 精确配速」无法同时满足。

解析式彻底消除取整：等级连续、配速可任意标定、跨版本不漂移。
增量表仍输出为精确整数写入常量表，作为**文档与回归基线**，运行时一律走解析式。

### 3.3 浮点边界（必须处理）

`cumulative_exp(6) = 78.5` 恰好落在等级切换点上，`log` 反解差一个 ulp 就掉回下一级。
校验中曾抓到 Lv6 与 Lv12 两处失配。真实积分里EXP 落在阈值附近是常态。

处理：`floor` 后做一次「本级阈值 + 容差（1e-6）」的上抬校正。
**往返一致性已验99/99 通过。**

## 五、升级解锁设计

EXP 只涨不花等于进度条。**升级必须解锁某种东西，且解锁的必须是事实记录，不是凭空属性。**

原则：解锁的是「你能看到什么」，不是「你变强了什么」。
这与项目既有约定一致 —— 逐核电压与历史基线**只展示、不计分**。

| 等级 | 解锁内容 | 类型 |
| ---: | --- | --- |
| 2 | 首次满负荷时刻 | 留档 |
| 5 | 当日贡献占比 | 统计 |
| 10 | 昼夜节律（白/夜负载比） | 统计 |
| 15 | 峰值留档（历史最高负载及日期） | 留档 |
| 20 | 连续出勤天数 | 统计 |
| 30 | 周对比（本周 vs 上周） | 统计 |
| 40 | 核心"小传"自动生成 | 叙事 |
| 50 | 活动热力（按时段 × 星期） | 可视化 |
| 60 | 与同封装峰值频率的差距走势 | 统计 |
| 70 | 全核齐飞/单核独跑记录 | 留档 |
| 80 | 月度归档与回看 | 统计 |
| 90 | 全时段负荷分布（直方图） | 可视化 |
| 95 | 异常事件回放（换人/跳档/越线） | 叙事 |
| 99 | 满级铭牌（可导出） | 叙事 |

**禁止**：任何 `+X% 性能`、`解锁超频`、`永久加成` 类文案。
**禁止**：逐核自检不得作为可重复的日常任务 —— 它会把每颗核拉到满载数秒，
做成打卡等于每天烧电。触发时机必须由数据决定（异常时建议排查），不由日程决定。

## 六、落盘方案

现有 `StatsStore` 只存"当天"，EXP 需跨日累积，另开账本：

| 文件 | 内容 |
| --- | --- |
| `core-exp.json` | 每物理核：`BusyCoreMinutes`、`ObservedSeconds`、`PeakPercent`、`PeakAt`、`MaxGhz`、`TotalLevels` |
| `core-exp.{旧口径}.json` | 口径变更时归档，只增不改 |

**必须写 `caliber` 标识。** 沿用 `energy-history` 的既有教训：
v1.21.0 口径从「CPU 封装功耗」换成「整机估算功率」时，
两种量不可比，只能整份归档重开，**不做换算** —— 硬折出来的历史只是"看起来完整"。
EXP 一定会改口径（例如从纯负荷改成负荷+陪伴兜底），这个坑要提前留好。

### 6.1 实现期修正：落盘有两个坑，都会静默丢数据

**(1) `System.Text.Json` 不能写 NaN/Infinity**

本工具通篇用 NaN 表示「读不到」，但序列器**拒绝**写非有限值：
`ArgumentException: .NET number values such as positive and negative infinity cannot be written as valid JSON`。

而 `Save` 内部的 `catch` 会把它吞掉 —— 结果是**账本根本没落盘，而界面毫无异常**。

修法：落盘用 `CoreExpRecord` 间接层，读数字段存 `string`，非有限值写 `null`，
读回时还原为 NaN。**绝不改成"存 0"或"null 按 0 读回"** —— 那正是本项目最忌讳的以 0 冒充缺失。
往返取证已断言：`PeakPercent: NaN` 落盘为 `null`，读回仍为 NaN。

**(2) 口径串含斜杠会毁掉归档**

口径写成 `load-core-minute/v1`（带版本号）后，归档目标成为
`core-exp.load-core-minute/v1.json` —— 其中的 `/` 被当作目录分隔符，
`File.Copy` 抛 `DirectoryNotFoundException`，**又被 catch 吞掉**，
结果是旧账本既没归档、也没被清空，静默丢失。

`EnergyHistoryStore` 侥幸没暴露这个问题，只因它的口径标识（`cpu-package`）不含斜杠。

修法：`Sanitize()` 把路径分隔符与非法字符一律替换为 `_`，空串返回 `unknown`
（否则会生成 `core-exp..json`）。断言：`load/v1` → `load_v1`、`a\b` → `a_b`。

### 6.3 界面接入（v1.22.0 已完成）

- `CoreLevelVm`（`ViewModels/Dashboard/`）：等级 / 进度 / 悬浮说明的 VM 层。
- `DashboardViewModel`：字段初始化即 `CoreExpStore.Load().Cores` 读回历史；
  `AccumulateSample` 内 `_exp.Accumulate(snapshots, delta)` 与负载**共用同一份 Δt**；
  `RefreshCoreLevels` + `SaveExpIfNeeded` 挂在 `ApplyHealthView` 之后。
- `CpuCoreTile.xaml`：标准卡与紧凑卡各加第 4 行（等级 + 进度细条 + 悬浮说明），
  **刻意不占健康度角标位** —— 角标是 0–100 硬件状态，等级是"陪你跑了多久"，
  语义无关，混在一起会让人以为「等级低 = 机器坏了」。
- 落盘节流：5 分钟**或** 1 核·分二者之一；首次落盘无条件执行。
- 峰值留档：只升不降，读不到时**保持 NaN**（不写 0）。

### 6.4 实现期修正：三处接入缺陷

**(1) 界面只喂累加器 → 重启后等级归零（最严重）**

`RefreshCoreLevels` 初版写 `vm.Level.Refresh(_exp.ExpCoreMinutes(id), ...)` —— 只取本次运行的
累加器，**完全没算上账本里的历史**。后果：每次重启每颗核都回到 Lv 1，
「跨进程延续」这个核心前提形同虚设。

界面渲染完全正常、无任何报错（每个Lv 1 都是"真的 0 经验"的正确显示），
**只有真机截图才能发现** —— 单元测试全绿时它照样是错的。

修正：`ledgerExp + runExp`。累加器覆盖"上次落盘之后"、账本覆盖"之前"，
两者区间不重叠，故相加而非取 max。已加回归断言（含反例固化：只喂累加器必然 Lv 1）。

**(2) 核心 Id 必须与实际拓扑一致**

账本按核心 Id 索引。取证脚本一度预置成 `P0..P7`，而实际平台是 `C0..C7` ——
账本读回了、一颗都匹配不上，界面显示 8 个正确的 Lv 1，同样毫无破绽。

**已知局限**：换平台 / BIOS 改 Id 会导致历史失配（表现为等级从 1 重新开始，
旧记录仍在账本里）。目前不做跨平台映射 —— 跨平台的"同一颗核"并无可靠定义。

**(3) `SegmentBar` 没有 `Minimum`/`Maximum`**

它的 `Value` 是 0–1 归一量程（与核心负载同一控件）。写 `Minimum="0" Maximum="100"`
编译直接报 MC3072。等级进度条应绑 `Level.Progress`（0–1）而非 `ProgressPercent`。

### 6.5 取证脚本的两个坑

- **`PrintWindow` 对本程序的软件渲染窗口返回全白**（实测 1800x1280 纯白），
  而同一次运行的 UIA 读取证明数据完全正确。改用 `PIL.ImageGrab.grab(bbox=窗口矩形)`。
- **ctypes 的 GDI 句柄在 64 位下溢出**：必须显式声明
  `GetWindowDC.restype = wt.HDC`、`CreateDIBSection.restype = wt.HBITMAP`、
  `SelectObject.restype = wt.HGDIOBJ` 及对应 argtypes，否则报 `int too long to convert`。

### 6.7 核角色系统（v1.22.0 第三批，已接入）

由**长期统计**派生的行为画像，与等级的分工：等级答「陪你跑了多久」，角色答「它是怎么跑的」。

**与 EXP 的三处口径差异（刻意不同，不可混用）**

| | EXP | 角色 |
| --- | --- | --- |
| 负荷 | 含陪伴兜底 | **纯负荷** |
| 平方项 | 不记 | 记（用于方差） |
| 昼夜 | 不分 | 按 08:00–20:00 / 20:00–08:00 切分 |

纯负荷是必须的：兜底会把「闲」抹成「轻」、「轻」抹成「勤」，两颗实际差10 倍的核会拿到同一角色。
昼夜切分让「夜猫子」成立（阈值：夜间占比 ≥ 62%）。

**判定顺序有意义**：形状特征（夜猫、尖峰）先于水平特征（摸鱼/稳态/苦劳）。
一颗只在夜里爆发的核，若先按均值判成「闲时热手」就丢掉了它最重要的特征。

| 角色 | 判据 |
| --- | --- |
| 夜猫子 | 夜间负荷占比 ≥ 62% |
| 尖峰侠 | 峰值 ≥ 90% 且 峰值÷均值 ≥ 5 |
| 摸鱼王 | 均值 < 8% |
| 苦劳 | 均值 ≥ 60% |
| 稳态搬运工 | 均值 ≥ 25% 且 变异系数 ≤ 0.35 |
| 闲时热手 | 其余（中等负载但波动大、或样本偏短） |

证据门槛：观测 ≥ 60 核·分（单核满载 1 小时）。不足一律 `Unknown` → 界面显示 `-`。

**判定用「账本 + 本次运行」的合并量**，否则重启后角色要重新积累很久才稳定 —— 与 EXP 同一个道理。

落盘间隔 15 分钟（比 EXP 的 5 分钟稀：统计量本身变化慢）。

### 6.8 实现期修正：一个静默失效的真bug

`CoreRoleStore.cs` 里的 `CoreRoleStore` 类被**嵌套进了 `CoreRoleEntry` 内部**（`CoreRoleEntry` 的类体少了一个 `}`）。

它的表现极具欺骗性：
1. App 项目编译**通过**（没有代码引用这个类，编译器不报错）；
2. 首次发现是探针工程报CS0234「命名空间里没有该类型」；
3. 加一行自引用探针后编译器才说出真相：`CS0722: CoreRoleEntry.CoreRoleStore`。

**教训**：C# 里「类被错误嵌套」不会让编译失败，只会让它在**外部不可见** ——
而"App 自己编译通过"会让人误判成运行时或引用问题。凡是跨文件可见性异常，
先用一行自引用探针把编译器的话逼出来，比逐层猜快得多。

## 六·补记：禁止静默吞异常

`Save` 的 catch 已从 `catch (Exception) {}` 改为记录 `CoreExpStoreTrace.LastSaveError`。
发布版没有界面消费它，但保留比彻底丢掉更有价值 ——
「账本根本没落盘」若完全静默，用户会以为等级一直在涨。
取证脚本会读取该字段并在失败时抛异常，让问题在验证阶段就暴露。

## 九、刻意的红线

1. 等级**不得**由健康度换算。
2. 进度轴**只能是**满负荷核·小时，不得出现寿命/磨损表述。
3. 结算页每个数字必须可追溯到具体来源，来源不可用时整条降级为 `-`，
   **绝不为了页面完整而补一个估计值**。
4. 缺观测的日期就是缺，不给补救机会；streak 只展示，不绑定日历质量。
