# CORE-BUSY 核忙

> 看看你的 CPU，谁在干活，谁在摸鱼。

一款用于实时观察 CPU 每个核心运行状态、负载、频率、温度、功耗和调度行为的 Windows 桌面监控工具。

![dashboard](docs/screenshot-dashboard.png)

## 技术栈

- C# / .NET 8
- WPF（自定义 WindowChrome 无边框窗口，PerMonitorV2 高 DPI）
- MVVM（UI 与数据完全解耦）
- 当前阶段全部数据由 `MockCpuMonitorService` 模拟驱动，接口与真实采集实现可无缝替换

## 运行

```bash
dotnet build CORE-BUSY.sln
dotnet run --project src/CoreBusy.App
```

启动后即显示完整仪表盘，按设置的采样周期真实采样刷新（默认 1000ms；热力图**恒为最近 60 秒**，与刷新周期解耦）。

> 提示：以管理员身份运行可解锁温度/功耗传感器（Ring0 驱动）；非管理员时温度降级为 ACPI 温区、功耗/风扇显示 "-"。
>
> 硬盘温度（状态栏）同属内核驱动路径，非管理员读不到。口径：**取 NVMe 的 Composite Temperature**（与 CrystalDiskInfo、任务管理器同口径），多块盘取最热；LHM 一并暴露的 `Warning/Critical Temperature` 是**阈值**不是读数，必须按名字排除（v1.16.2 修：曾把 87/114 ℃ 的临界线当成实时盘温显示）。悬浮详情逐块列出型号与温度。
>
> CPU 风扇（v1.16.3）：台式机走 LHM 的主板 SuperIO；**笔记本不在 LHM 的采集范围**（ASUS 机型整棵硬件树里没有 `Fan` 传感器，`0.9.6` 也无 EmbeddedController 开关），改由 ASUS 自家的只读 ACPI 接口补齐 —— WMI `root\wmi` 类 `AsusAtkWmi_WMNB` 的 `DSTS` 方法，CPU `0x00110013` / GPU `0x00110014`，返回值低 16 位 ×100 = RPM。该接口同样**只对提升后的进程开放**（非提权时连类枚举都"拒绝访问"），且本机不存在的端点会返回 `0xFFFFFFFE` 哨兵值，必须挡掉（v1.16.3 实测：中置风扇 `0x00110031` 即为此类）。悬浮风扇那一行可看到 CPU/GPU 分项与来源（或读不到的原因）。

## 构建与发布

`scripts/` 下的三个脚本覆盖了从环境准备到交付产物的全流程，**不依赖 shell**（本机沙箱 bash 缺少 Windows 系统环境变量，直接 `dotnet` 会报 `Value cannot be null (path1)`）：

```bash
# 1. 准备 .NET SDK（zip 解压到 ~/.workbuddy/binaries/dotnet-sdk，非全局安装）
python scripts/setup-dotnet-sdk.py

# 2. Release 构建 + 单文件发布 + 打包
python scripts/build-release.py

# 3. UI 静态检查（无 SDK 也能跑）
python scripts/lint_ui.py
```

| 脚本 | 作用 |
| --- | --- |
| `setup-dotnet-sdk.py` | 按约定版本（8.0.425）下载并解压 SDK 到 `~/.workbuddy/binaries/dotnet-sdk`；已存在则跳过。`--force` 强制重装，`--version X` 换版本 |
| `build-release.py` | `dotnet build` → `dotnet publish -r win-x64 --self-contained -p:PublishSingleFile=true` → 复制 `dist/CoreBusy.App.exe` → 打包 `dist/CoreBusy-v{版本}-win-x64.zip`。日志写 `build-log.txt`。`--no-publish` 只编译 |
| `lint_ui.py` | 校验全部 `.xaml` 的 XML 结构，并把每个 `{Binding X}` 与 C# 公开成员比对。WPF 对拼错的绑定路径只写 trace、界面静默空白，此检查用于提前拦截这类缺陷 |
| `make_icon.py` | 生成应用图标 `src/CoreBusy.App/Assets/CoreBusy.ico`（16/20/24/32/40/48/64/128/256 九档）。每个尺寸**独立重绘**而非缩放，`≤24px` 自动切简化稿；同时输出预览图 `docs/icon-preview.png` |

> `build-release.py` 在 `dist/CoreBusy.App.exe` 被运行中的实例锁住时不会崩掉：
> 压缩包仍从发布输出生成，只跳过 dist 镜像复制并以退出码 2 提示（关闭程序后重跑即可）。

发布产物（`dist/`）：

| 文件 | 说明 |
| --- | --- |
| `CoreBusy.App.exe` | **单文件自包含**可执行文件（约 159 MB）。本机无系统 .NET 8 运行时，故必须 self-contained，双击即可运行 |
| `CoreBusy-v{版本}-win-x64.zip` | 压缩包，仅含上述 exe，用于分发 |
| `_publish/` | 发布中间产物（exe + 各项目 pdb） |
| `logs/debug.log` | 运行日志（启动版本号 / 主题 / 采样配置 / 不变量告警），写在 exe 同级目录 |

> **为什么完整版不再压缩**（v1.19.0）：单文件压缩会把全部托管程序集在启动时解压进内存。
> 实测（`measure_footprint.py`，同一台机器、隔离数据目录）：
>
> | 发布方式 | 文件 | 稳定工作集 | 稳定提交 |
> | --- | --- | --- | --- |
> | 单文件 + 压缩（v1.18.0 及以前） | 70 MB | 252 MB | 132 MB |
> | 单文件 + 不压缩（v1.19.0 起） | 159 MB | 154–170 MB | 68–80 MB |
>
> 即压缩用约 **85 MB 工作集 / 60 MB 提交换来 89 MB 的体积**。对一个常驻托盘盯着 CPU 的
> 小工具，运行内存比下载体积要紧，故放弃压缩。想要小体积可改用精简版通道
> （[`--variant lite`](scripts/build-release.py)，exe 4.9 MB，需系统装一次 .NET 8 桌面运行时）。
> （v1.19.0 的精确值随采样窗口上下浮动 —— `ConserveMemory` 开启后 GC 会主动把空代数归还 OS，
> 工作集在两个档位间来回，属预期行为而非泄漏：稳定期首末差为正负几 MB 量级。）

> 版本号取自 `src/CoreBusy.App/CoreBusy.App.csproj` 的 `<Version>`，并同步显示在状态栏。改动版本号时请一并更新状态栏文案。

## 线程粒度呈现

同一份数据用两种粒度呈现，保证 CPU 的**核心数**与**线程数**同时完整可见（不会出现"标称 16 线程、界面只有 8 格"）：

| 位置 | 粒度 | 表现 |
| --- | --- | --- |
| 核心分区 Tile | 物理核 | 一格一颗物理核。SMT 核（AMD Zen / Intel P-Core）在格内展开 `T0` / `T1` 两条线程条并替代核级聚合条；单线程核（Intel E-Core、关闭 SMT）只显示核级条 |
| 60 秒热力图 | 逻辑线程 | 一行一条线程（`C0·0` / `C0·1`），8/16/20/32 线程平台均一屏铺满，不滚动 |

数据来源是 `CpuCoreSnapshot.Threads`（`CpuThreadSnapshot[]`，与核心快照同源、同一次采样）：
真实采集按拓扑的 `OsIndexes` 逐线程取 `% Processor Time`；Mock 按平台线程数（P 核 2 / E 核 1 / 无 SMT 为 1）生成。Tile 内线程条与热力图行**不会出现两份口径打架**。

## 核心分区口径（规范 / 设计稿）

分区由采集服务的 `ICpuMonitorService.GetCoreGroups()` 元数据驱动，界面不硬编码任何固定分组。

| 平台 | 规范口径（默认） | 设计稿口径 |
| --- | --- | --- |
| Intel 混合架构（12 代及以后） | `P-Core`（P0..Pn）+ `E-Core`（E0..En），真实物理核聚合 | 同左 |
| Intel 非混合架构 | 单段 `CPU Core`，核心名 C0..Cn | 逻辑线程对半拆成 P / E 两段 |
| AMD 单 CCD Ryzen | 单段 `CPU Core`，核心名 C0..Cn | 逻辑线程对半拆成 P / E 两段 |
| AMD 多 CCD Ryzen | `CCD 0` / `CCD 1` …，核心名跨 CCD 连续编号 | 逻辑线程对半拆成 P / E 两段 |

- **AMD 绝不出现 P-Core / E-Core**（规范硬性要求）；`CoreClass.Standard` 是 AMD 与非混合 Intel 的唯一类别。
- CCD 数按「Zen 消费级单 CCD ≤ 8 核」的公开架构约束由物理核数推导（12/16 核 → 2 CCD）；
  >16 核的 HEDT/服务器平台不做猜测，回退单段。X3D 的 3D V-Cache 标注**无数据确认时一律不显示**。
- 拓扑退化场景（虚拟机/云主机只暴露单条核心掩码）按 SMT 口径还原物理核数（16 线程 → 8 核），
  与任务管理器一致。

## 核心负载口径：实时 / 累积

核心分区标题右侧可切换两种口径，**同一张卡片、同一套色阶**，只是换了读数含义：

| 视图 | 大号数值 / 进度条 / 左侧色条 | 左下槽位 | 右下槽位 | 列表顺序 |
| --- | --- | --- | --- | --- |
| **实时**（默认） | 瞬时使用率 | 频率 | 状态标签（摸鱼/空闲/工作/忙碌/高负载/爆肝） | 自然核序 C0..Cn |
| **累积** | 运行期累积均值 0-100% | 等效满负荷量（核·秒 / 核·分 / 核·时，按量级自动换档） | 名次 `#n / 总数` | **按累积均值降序**（全局排名） |

累积均值定义为 `Σ(使用率% × Δt) / Σ(Δt)`，即运行期内在该核上的平均占用百分比。三个设计取舍：

- **时间加权而非逐帧求和**：采样周期可被用户改档（500/1000/2000ms，性能模式另有 2000ms 覆盖），
  按帧累加会让周期长的那次权重翻倍——同一段负载换个档位就得出不同结论。Δt 一律取**墙钟差**。
- **归一化到 0-100**：均值与实时使用率共用同一套色阶与进度条，界面不需要为累积视图引入第二套刻度。
  未归一化的等效满负荷量（核·秒）作为绝对量感放在左下槽位。
- **始终积分**：积分与当前视图无关地一直在跑，因此切到累积视图立刻有完整历史，而不是从切换那刻才从零开始。
  标题右侧的「重置」可清零重新统计。

排名做了**滞回**（相邻两核累积均值差距不足 0.4 个百分点不换位）：换位会重建该分区的
`ItemContainer`（新 `SegmentBar` 从 0 动画到目标值），均值接近的核若每帧互换，界面会持续闪动且白白消耗 CPU。
另有一条运行期不变量断言守着「名次必须是 1..N 的排列、且分区显示顺序按名次降序」——
名次一旦退化成自然顺序，界面看起来完全正常、数据却是错的，只有日志能说明问题。

## 运行期累计能耗（状态栏）

状态栏「运行」右侧显示运行以来的累计耗电，口径是 `Σ(封装功耗W × Δt)`，
单位按量级自动换档（mWh → Wh → kWh）。Δt 与累积负载**共用同一份墙钟差**：
两路累计描写同一段时间轴，若各自维护基准，一次休眠后可能只跳过其中一路，两个窗口就此错开。

选 Wh 而非焦耳作为主显单位，是因为它落在日常经验的量级上（笔记本电池约 60 Wh），
同一份能量用焦耳表示会是六位数起步的天文数字，读不出量感。

**它和累积负载有一处关键差别：数据源可靠性。** 使用率来自 Performance Counter，永远可读；
封装功耗来自硬件传感器（需管理员权限加载内核驱动），在非管理员会话、传感器被设置关闭、
性能模式暂停轮询时都会变成 `NaN`。因此这里维护**独立于负载的第二个时间基准**，并据此做了两件事：

| 情形 | 显示 | 理由 |
| --- | --- | --- |
| 有读数 | 亮色数值 + 悬浮提示 | 提示里给出统计窗口、**传感器覆盖率**与平均功率 |
| 中途读不到 | 数值冻结并转**弱色** | 表示它已停止更新，不是一个仍在累积的实时数 |
| 从未读到 | `-` | **不拿 0 冒充**：0 Wh 断言这段没耗电，`-` 只是说不知道，两者完全不是一回事 |

覆盖率会出现在悬浮提示里。传感器断过一段时间后再看累计量，它只代表「观测到的那部分时间」——
这句话必须写出来，否则用户会把部分时段的结果当成全程结果来读。

读数还做了合理性筛选（`0 ≤ P ≤ 1000W`）：某些平台偶发返回单位错误的离谱读数，
这类异常值一旦参与积分会永久污染累计量。

## 主题

| 主题 | 触发 | 说明 |
| --- | --- | --- |
| Intel Blue | CPU 为 Intel，或设置中手动锁定 | 深蓝基底 + 蓝色边缘辉光，热力图 深蓝→蓝→青→浅青 |
| AMD Red | CPU 为 AMD，或设置中手动锁定 | 近黑基底 + 红色边缘辉光，热力图 黑→暗红→红→橙（越亮负载越高） |
| Neutral | 厂商未知，或 `COREBUSY_FORCE_BRAND=neutral` | 中性石墨基底 + 低饱和蓝强调 |

- 设置里可选「自动 / Intel Blue / AMD Red」；默认自动跟随 CPU 厂商。
- 高负载（≥80%）在三种主题下统一用红色，危险语义跨主题一致。
- CPU 身份徽章（型号旁的 AMD/intel 标记）**始终反映真实厂商**，不随主题变化。
- 主题与核心分区在窗口构建前生效（`StaticResource` 解析时机），修改后需重启应用；主窗口会提示并可一键重启。

| 按钮 | 行为 |

| 更多 | 打开运行日志文件夹（`<exe目录>/logs`）。 |

## 架构说明

- **数据接口**：`ICpuMonitorService`（`GetCpuInfo / GetSnapshot / GetCoreSnapshots`）是 UI 与硬件采集的唯一边界。`WindowsCpuMonitorService` 组装真实采集（默认注入），`MockCpuMonitorService` 作为回退；UI 无感知。
- **采样模型**：真实服务在后台线程按 `SampleInterval` 采样（占用率/传感器/进程），UI 定时器读取最新快照，两端解耦；采样周期可经设置 / 性能模式在运行时调整。
- **状态分类**：`CoreStatusClassifier`（0-5 摸鱼 / 5-20 空闲 / 20-50 工作 / 50-80 忙碌 / 80-95 高负载 / 95-100 爆肝）。
- **配色体系**：全部颜色集中在 `Themes/Colors.xaml`、`Themes/Brushes.xaml` 与 `Themes/BrandTheme.cs`（按品牌装配），组件内不散落硬编码。
- **品牌主题**：`BrandTheme.Apply(vendor, themeMode)` 装配整套视觉。三品牌**共用同一套中性深灰层次基底**（背景 `#1A1A1A` → 面板 `#232323` → 卡片 `#2B2B2B` → 描边 `#3D3D3D`，靠**明度分层**而非透明度），**唯一差异是强调色**：AMD `#E0524A` / Intel `#4CA0E0` / 中性 `#5AB8E8`。v1.7.0 已移除径向辉光（旧版 3 层辉光叠加会把整窗染成品牌色、压平全部对比度）。命名空间/文件结构沿用 v1.5.0 的单文件装配（规范 §5「一套 Layout + 两套主题资源」已满足；§4 的 `CoreBusy.Themes` 目录拆分属建议项，未拆）。主题在主窗口构建前应用（StaticResource 解析时机）。
- **核心分区**：`CpuCoreGroup`（`CoreGroupKind` + 分区内核心名）由 `WindowsCpuMonitorService` / `MockCpuMonitorService` 产出，`DashboardViewModel.BuildCoreGroups` 转成 `CoreGroupVm` 集合，界面用 `ItemsControl` 动态渲染——新增平台形态无需改 XAML。
- **已移除的模块（v1.7.0）**：排行榜（劳模榜 / 摸鱼榜）与「最忙的核心」面板。ViewModel 侧仍有对应属性（`BusyRanks` / `IdleRanks` / `TopCore*` / `PeakSeries`）处于"已计算但无绑定"状态，`Controls/RankingPanel.xaml`、`Controls/CpuSummaryCard.xaml` 也已无 UI 引用 —— 属待清理的技术债（v1.19.0 已把这几项的计算改为**零分配**，属性语义不变，等真要清理时不必再动性能）。
- **托盘图标（v1.19.0）**：换成 WPF 原生实现 `Infrastructure/TrayIcon.cs`（`Shell_NotifyIcon` + 隐藏消息窗口 + WPF `ContextMenu`），不再引用 `System.Windows.Forms`。此前托盘是 `UseWindowsForms=true` 的唯一用途，而它会把 `System.Windows.Forms.dll`(13.5 MB)、`.Primitives`(3.0 MB) 与 `System.Drawing` 一并带进产物与启动加载。要求图标资源缺失时退到系统通用图标并记日志 —— 「窗口藏进托盘但托盘里没图标」是用户无法自救的状态。
- **热力图**：`HeatMapControl` 最低色档（0-8%）刻意高于面板底色亮度（对比 ≈ 2.5:1），并铺一层网格底板，保证空闲负载下 60×N 的网格结构依然清晰可辨；面板右上带 7 档色阶图例（低→高），面板设 MinHeight 防止窗口缩小时被压没。
- **核心数显示**：退化拓扑平台（虚拟化等）按 SMT 口径估算物理核心数（16 线程 → 8 核 / 16 线程），与真实设备规格一致。
- **刷新平滑**：分段条/进度条/环形仪表内置 `ValueAnimator`（指数趋近动画），数据按帧平滑过渡而非生硬跳变；动画器带**共享帧闸门**（60fps → 30fps），接近目标后自动摘除渲染钩子，空闲时零开销。
- **热力图绑定**：`Heatmap` 每次刷新都产出**新的数组实例**（不可原地改同一数组——WPF 依赖属性按引用比较，值未变则不触发 `AffectsRender`，OnRender 只跑首帧会导致整片热力图冻结）。列推进按**墙钟秒**计算，保证 60 列恒等于 60 秒，与刷新周期解耦。
  > ⚠ **v1.19.0 实测踩过同族但更隐蔽的一版**：`PushHeatmap` 曾写成先 `_heatmap = next;`（直赋后备字段）再 `Heatmap = next;`（走 `SetProperty`）。`SetProperty` 按引用比较，此时"新值 == 旧值"→ **永不发 `PropertyChanged`** → `HeatMapControl.RowsData` 恒为 `null` → `OnRender` 开头的空值判断直接 `return`，**整片热力图（连网格底板）都不画**。运行期不变量（`VerifyHeatmapInvariants`）校验的是行数，而字段确实被更新了，所以一路静默通过、日志一行不写 —— 只有截图能发现。改法：**只走属性 setter，不要先动后备字段**。
- **性能**：热力图/分段条/环形图/Sparkline 均为纯 `OnRender` 自绘控件，刷新时不重建视觉树；画刷全部冻结共享；**卡片不使用 DropShadowEffect**（避免每帧高斯模糊重渲染）；热力图格用直角矩形而非圆角（960 格/次的重绘开销）。实测自身占用：1000ms 采样约 0.36% 整机口径，性能模式（2000ms + 关传感器）约 0.2%。
- **每帧零分配（v1.19.0）**：热力图矩阵改为**两组行数组交替原地滚动**（旧实现每秒新建 16×60 的锯齿数组，约 8 KB/s 垃圾）；Sparkline 序列同法双缓冲；劳模榜 / 摸鱼王 / "最忙的核心"由 3 次 LINQ 排序改为**单次遍历的有界插入**（排序语义逐字对齐，含同率按核心名定序）。发布仍按"引用必须变"的约束交替新实例，否则依赖属性会被 WPF 判为未变化而不再重绘。
- **已实测否决：`InvariantGlobalization`（v1.19.0 试过，当前未启用）**。它一度能测出省约 30 MB 工作集，但**WPF 与它不兼容**：每个 `FrameworkElement` 的 `Language` 默认是 `XmlLanguage("en-US")`，数据绑定取值要把它转成具体 `CultureInfo`，而 Invariant 模式下创建任何非不变区域性都会抛 `CultureNotFoundException` → **每一条数据绑定都在 `Window.Show()` 阶段抛异常**。异常被 `App.OnDispatcherUnhandledException` 吞掉（`e.Handled = true`），外部表现是"进程存活、内存还降了、日志里只有一行 `DISPATCHER UNHANDLED`，而主窗口从未渲染出来"。因此那批"省 30 MB"的数据是在**界面根本没画**的前提下测的，全部作废。**不要重新打开此项**，除非同时解决 WPF 的区域性依赖（例如全局 `OverrideMetadata(FrameworkElement.LanguageProperty, …)`）。
- **GC 内存节流**：`System.GC.ConserveMemory = 5`（csproj 里用 `<RuntimeHostConfigurationOption>` 直投）。注意 **`-p:GCConserveMemory=5` 在本 SDK（8.0.31）下不会落进 `runtimeconfig.json`** —— 属"以为开了其实没开"的静默失效，必须用 `RuntimeHostConfigurationOption` 并回读产物确认。
- **渲染模式**：默认 `SoftwareOnly`，且**这是实测更省内存的一档**。同一份 v1.19.0 产物、同一台机器（Console 会话、AMD 核显）、同样的真实配置（传感器开、1 Hz），只改环境变量对照 60 s：
  | 渲染模式 | 稳定工作集 | 稳定提交 | 稳定期 CPU |
  | --- | --- | --- | --- |
  | 软件（默认） | 154–170 MB | 68–80 MB | 0.06 核 |
  | 硬件 | 192–199 MB | 111–119 MB | 0.05 核 |
  即硬件加速在这台机器上多占约 **35 MB 工作集 / 45 MB 提交**，却换不到可测的 CPU 收益（画面 1 秒才动一次，自绘控件全部走冻结画刷 + 零分配，渲染路径不是瓶颈）；何况远程会话下 D3D 渲染面在 Hide/Show 后易丢失（客户区变黑）。**省内存与"远程不黑屏"指向同一个选择**，故不做"按会话类型自动切换"。逃生开关：`COREBUSY_SOFTWARE_RENDER=0` 试硬件加速、`1` 显式锁软件，**不设 = 默认软件渲染**；决策结果写进 `logs/debug.log`。
  > 注：早先一版对照数据（软件 151/85、硬件 195/138）是在热力图因绑定缺陷**没有绘制**的产物上测的，虽方向一致但已作废，上表为重测值。

## 核心健康度评分（v1.18.0）

每个核心 Tile 上带一个 **0–100 的健康度角标**（悬浮展开评分依据），CPU 概览另有一行汇总均分与最低核。
它是一个**合成代理指标**，不是厂商认证的"损耗百分比"——CPU 没有可读的健康度寄存器
（不像电池有标定容量、SSD 有 P/E 计数），本功能能做的是把可观测量合成成一个分数并**说清依据有多硬**。

| 分量 | 权重 | 口径 | 读不到时 |
| --- | --- | --- | --- |
| A · 频率达成度 | 60% | 该核**有效频率**峰值 ÷ **同封装各核峰值中位数**（允许 5% 自由带） | 频率缺失 → 无频率；证据帧/参照不足 → 三项一并不给分 |
| B · 热裕度 | 25% | 封装温度距 95 ℃ 的余量；70 ℃ 以内不扣分，**全核共担** | 温度读不到（非提权）→ 缺席，权重由剩余分量归一化，覆盖率随之下降 |
| C · 时钟稳定性 | 15% | 满载窗口内频率的鲁棒变异系数（MAD） | — |
| WHEA | 作用于总分 | 近 7 天已纠正硬件错误每条 −5、封顶 −25；存在未纠正错误则总分封顶 60 | 读不到与"读到 0 条"严格区分（不拿 0 冒充） |

- **证据判据（v1.18.0）**：OS 使用率 ≥ 70% **或** 硬件活跃度 ≥ 70%（取"或"）。前者是调度器视角、
  独立于传感器（频率读不到时仍可用）；后者（有效频率 ÷ 本机最高加速档）是硬件视角，不受 SMT 共享
  与频率门控失真影响。累计 **≥ 3 个证据帧**就评分 —— v1.17.0 要求 8 帧（≈ 连续满载 8 秒），
  真实使用中很难满足，那正是用户看到"一整屏 `-`"的原因。样本不足时一律显示 `-`，**绝不拿 0 冒充**。
- **频率口径（v1.18.0 的核心改动）**：判分走 LHM 的逐核**有效频率** —— 硬件驻留加权的时间平均值，
  一颗 5% 负载的核即使瞬时冲到 4.5 GHz，一秒平均下来也只有 200 余 MHz。它同时回答了
  "实际跑多快"与"是否真的在执行"。**P-state 档位时钟不能判分**：那是离散档位、与负载无关，
  本机 8 颗核会读到同一个 4567 MHz → 比值恒 1 → 人人满分（它仍用于 Tile 上的频率显示）。
  有效频率缺失时降级到档位时钟并**在界面标注口径**；**读到 0 是真实读数**（该核整秒未执行），不降级。
- **帧距下限 0.9 秒**：turbostat 明确警告测量区间不应短于 1 秒。用户把刷新周期调到 200 ms 时，
  健康统计按 ~1 秒节拍取帧（界面刷新照旧快），判定口径不随显示偏好漂移。窗口 240 帧。
- **参照有效性闸（v1.18.0）**：达标核 < `max(3, ⌈已跟踪核数 ÷ 2⌉)` 时**全体一律不给分**。
  中位数在 1–2 个点时会退化成"某一颗核自己"→ 比值恒 1.0 → 总分 100。v1.17.1 实机出现过
  `100 / 最低 C1 100`，而那一刻 8 颗核里只有 **1 颗**达标。**`-` 是诚实的"没有证据"，`100` 不是。**
  未给分会带出原因（`无频率` / `样本不足` / `参照不足`），概览行给出进度如 `- · 参照不足 1/4 核`。
- **峰值估计量（v1.18.0）**：升序序列中**最好四分之一帧的均值**（下限 2 帧），取代 90 分位 ——
  后者在 8 个样本时**数学上就是最大值**，会把冷启动瞬时高峰钉成永久锚点。
- **分档**：≥ 90 良好 / 80–89 正常 / 70–79 需关注 / < 70 异常。
- **参照只有一个来源**：同封装各核峰值的**中位数**。不用最高分位当标尺——实机八核峰值天然散布
  3.86–4.24 GHz（体质分档），拿"最好的那颗"比会把大半核心报成异常。
- **逐核电压只展示、不计分（P2）**：读到时在角标悬浮里展示并记入 `core-voltage.json`。
  "同频所需电压上升"虽是硅老化最灵敏的信号，但要成为分数需要一个**标定过的同频点**，
  而本工具不写 MSR、不控频，拿不到这样的点；硬折成分数就是拿工况当结论。
- **纵向基线只展示、不计分**：`%APPDATA%\CORE-BUSY\core-health.json` 记录每核历史最好"站位"
  （相对同伴的比值，无量纲，天然免疫散热/功耗工况的整体漂移）。但"取历史最大值当锚"这个估计量
  自身带 **~2.5% 的系统性偏差**，大于数年尺度的真实硅老化，折成分数只是在报估计噪声。
- **诚实边界**：本功能衡量"**这颗核现在相对同伴健不健康**"，不衡量"整颗芯片相比半年前掉了多少"。
  后者要真正计量，需要的不是更好的算法而是更好的观测量（固定电压下的 V/F 曲线——要写 MSR，本工具不碰）。

### 逐核确定性自检（P3，用户显式触发）

CPU 概览标题行右侧的 **「自检」** 按钮：依次把每颗核的**全部逻辑处理器**绑上，跑一段**结果已知**的
计算 —— 同一次卷积用 NTT 与 O(n²) 直卷积两条**独立路径互证**（任何一处 ALU / 访存 / 缓存错误
都会让它们不一致），再要求浮点输出**比特级复现**（比对位模式而非数值容差，因此不存在
"阈值定得松紧"这种可争辩的空间）。

- 这是唯一能**确定性**判定"这颗核算错了没有"的手段 —— 频率、电压、温度都只是间接推断。
- 每核默认 2 秒、上限 10 秒：它是采样，不是烤机。运行中按钮变「停止」，可随时中断。
- 结果写入 `%APPDATA%\CORE-BUSY\core-selftest.json`：首次通过时记下校验和作为期望值，
  之后每次与它比对 —— **跨运行的不一致本身就是故障信号**，不需要外部"标准答案"。
- **不进评分**：一次 2 秒的自检通过不能证明一台机器健康，而失败属"要么 0 要么 1"的事件，
  折进 0–100 的连续分数只会稀释它的锋利度。
- 方法论借鉴 Prime95 / mprime，**不使用其代码或二进制**（其 EULA 明确非 FOSS，涉及 EFF 悬赏归属）。

- 判读用取证行：`[HEALTH]`（评级跨档）+ `[HEALTH·表]`（120 s 一次全表心跳）+ `[SELFTEST]`（逐核结论）。
