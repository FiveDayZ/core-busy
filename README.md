# CORE-BUSY 核忙

> 看看你的 CPU，谁在干活，谁在摸鱼。

Windows 下的逐核 CPU 监视器：实时显示每颗物理核的负载、频率与健康度，并给出 60 秒负载热力图、
CPU 概览、能耗日历和主要负载来源。

![CORE-BUSY 主界面](docs/screenshot-dashboard.png)

## 功能

| 功能 | 说明 |
| --- | --- |
| 逐核状态 | 一格一颗物理核；SMT 核在格内展开 `T0` / `T1` 线程条。可切换**实时 / 累积**两种口径 |
| 60 秒负载热力图 | 每逻辑线程一行 × 60 秒列，颜色越亮负载越高；恒为最近 60 秒，与刷新周期解耦 |
| CPU 概览 | 环形总使用率 + 温度 / 功耗 / 频率 / 风扇，全部指标的唯一来源 |
| 核心健康度 | 每核 0–100 角标（悬浮展开评分依据）+ 汇总均分与最低核 |
| 逐核自检 | 「自检」按钮：同一次卷积用 NTT 与 O(n²) 两条独立路径互证 + 浮点比特级复现，确定性判定某颗核是否算错 |
| 能耗日历 | 按月每天一格，档位判据是**当日平均功率**（整机估算口径）而非累计焦耳 |
| 状态栏能耗 | 运行期累计两路并排：`CPU` 封装能耗（传感器实测）│ `整机`能耗（估算，带 `≈`） |
| 主要负载来源 | 进程 TOP5（图标 + 占用 + 水平条） |
| 常驻与省电 | 托盘常驻；性能模式（刷新降为 2000ms 并暂停硬件传感器轮询）；主题跟随 CPU 厂商 |

## 下载与运行

从 [Releases](https://github.com/FiveDayZ/core-busy/releases) 下载 `CoreBusy-v{版本}-win-x64.zip`，
解压后双击 `CoreBusy.App.exe` 即可 —— **单文件自包含**，无需安装 .NET 运行时。

> **权限**：以管理员身份运行才能读温度 / 功耗 / 风扇（需 Ring0 驱动）。
> 非管理员时温度降级为 ACPI 温区、功耗与风扇显示 `-`；硬盘温度同属驱动路径，非管理员读不到。
> 读数一律**不拿 0 冒充**：读不到就是 `-`。

从源码构建（本机无系统 .NET，脚本会把 SDK 解压到用户目录，不做全局安装）：

```bash
python scripts/setup-dotnet-sdk.py     # 恢复 .NET SDK 8.0.425
python scripts/build-release.py        # Release 构建 → 单文件发布 → 打包
python scripts/lint_ui.py              # XAML 结构 + 绑定完整性静态检查
```

## 界面组成

| 区域 | 组件 | 说明 |
| --- | --- | --- |
| 顶部标题栏 | `MainWindow` | Logo + CPU 型号规格 + 性能模式 / 设置 / 打开数据文件夹 + 窗口按钮 |
| 核心分区 | `CoreGroupVm` | **动态分区**：Intel 混合 = P-Core + E-Core；AMD 多 CCD = `CCD 0` / `CCD 1`；其余单段 `CPU Core`。列数上限 4，窄窗自动折行 |
| 60 秒热力图 | `HeatMapControl` | 纯 `OnRender` 自绘，8/16/20/32 线程平台均一屏铺满、不滚动 |
| CPU 概览 | `CpuOverviewPanel` | 环形表 + 温度 / 功耗 / 频率 / 风扇 + 健康度汇总 + 自检入口 |
| 能耗日历 | `PowerCalendarPanel` | 月视图，每天一格；图例：少 → 多 色带 + 「不定档」 |
| 主要负载来源 | `ProcessListPanel` | 进程 TOP5 |
| 底部状态栏 | `StatusBarControl` | 版本 + 内存 / 显卡 / 磁盘 · 运行状态 + 运行时长 · `CPU` 能耗 │ 整机能耗 |

窗口默认 900×640（最小 880×600）。**AMD 绝不出现 P-Core / E-Core**：`CoreClass.Standard`
是 AMD 与非混合 Intel 的唯一类别；拓扑退化（虚拟机只暴露单条掩码）按 SMT 口径还原物理核数。

## 核心负载口径：实时 / 累积

核心分区标题右侧可切换，同一张卡片、同一套色阶，只换读数含义：

| 视图 | 大号数值 / 进度条 | 左下 | 右下 | 列表顺序 |
| --- | --- | --- | --- | --- |
| **实时**（默认） | 瞬时使用率 | 频率 | 状态标签 | 自然核序 C0..Cn |
| **累积** | 运行期累积均值 0–100% | 等效满负荷量（核·秒 / 分 / 时） | 名次 `#n / 总数` | 按均值降序 |

累积均值 = `Σ(使用率% × Δt) / Σ(Δt)`，Δt 一律取**墙钟差**（采样周期可被改档，按帧累加会让周期长的那次权重翻倍）。
积分始终在跑，与当前视图无关，因此切到累积视图立刻有完整历史；标题右侧「重置」可清零。

状态分档：0–5 摸鱼 / 5–20 空闲 / 20–50 工作 / 50–80 忙碌 / 80–95 高负载 / 95–100 爆肝。

## 能耗日历

- 每格 = 当天的**平均整机功率**（`焦耳 ÷ 观测秒数`，与状态栏「整机」那一路同源），
  档位相对「本月达标日平均功率的中位数」分 5 档。
- **累计焦耳不能直接比较**：它等于平均功率 × 观测时长，程序开了多久会污染结论
  （真机实测 4 天累计值相差 3.08 倍，平均功率只差 1.54 倍）。
- 当日观测不足 1 小时 → 该日**不定档**（独立紫灰色，不与「无记录」混用）；参照达标日不足 3 天 → 整月不定档。
- 账本文件里写明**口径**（`caliber`）。v1.21.0 起口径由「CPU 封装功耗」换成「整机估算功率」：
  两种量不可比，读到口径不符的文件会**整份归档**为 `energy-history.{旧口径}.json` 并重新开始。
  不做换算 —— 换算需要当时的分项系数，已经无从复原，按比例硬折出来的历史只是「看起来完整」。

## 状态栏能耗：两路并排

状态栏「运行」右侧是两项运行期累计耗电，中间用竖线分隔 —— **两路口径不同，必须视觉上分开**，
否则同为 Wh 量级、同样自动换档的两个数会互相冒充：

| 项 | 口径 | 来源 |
| --- | --- | --- |
| `CPU` | `Σ(封装功耗W × Δt)` | 硬件传感器**实测** |
| `整机` | 先按**逐部件**求和（CPU 实测 + 显卡 / 内存 / 硬盘 / 风扇 / 主板），再乘校准乘数，然后同样积分；数值带 `≈` | **估算** |

单位按量级自动换档（mWh → Wh → kWh）。中途读不到传感器时两路**同时**冻结并转弱色
（两路共用同一份 Δt 与同一份有效性判定，不允许一个在走、一个停了），
从未读到显示 `-`（**不拿 0 冒充**）；悬浮提示给出统计窗口与**传感器覆盖率**，
整机那一路另给出**逐部件构成**（每项分别标注是实测还是模型、用的什么额定值 / 系数）
与五个分项系数的所在位置。

### 整机能耗是估算，不是实测

本工具**没有**整机功率来源。在目标机上逐条排除过：LibreHardwareMonitor 的整棵硬件树里只有 CPU
有功率传感器；Windows 能耗计量接口（`GUID_DEVICE_ENERGY_METER`）枚举为空；无电池、无外接功率计；
`\Power Meter` 计数器集存在但无实例。因此整机功耗只能估算，原则是**能测就测，测不到按型号估**：

| 部件 | 口径 | 读不到时 |
| --- | --- | --- |
| CPU | 封装功耗**实测**（传感器） | **整条不出数** —— 绝不按 TDP 硬猜，否则会出现「左边 `-`、右边有数」 |
| 显卡 | 独显功率传感器**实测**（NVML / ADL），多卡按块求和 | 按型号额定功耗 × 负载曲线；**核显**功耗已含在封装读数内，不重复计；型号判别不出的如实标「未计入」 |
| 内存 | 容量 × 每 GB 系数（默认 0.392 W/GB，取自 Cloud Carbon Footprint）× 代际 × 占用率 | 消费级平台无此传感器，恒为型号模型 |
| 硬盘 | **逐盘**空闲（NVMe 1.2 / SATA SSD 0.6 / 机械盘 4.5 W）+ 摆幅 × 活动度 | 活动度依次回落到读 / 写吞吐 → 忙率 → 空闲档 |
| 风扇 | 转动个数 × 单扇系数（默认 2 W） | — |
| 主板等 | 固定开销（默认 10 W） | — |

- **与旧版「`k × CPU封装 + b`」的区别**：单斜率把 CPU 之外的一切压进一个斜率，
  带独显的机器上会整体漏掉一两百瓦（独显功耗不随 CPU 封装功耗线性变化）。
- 估算越界（分项系数被填成一组互相矛盾的极端值）时**拒绝出数**，提示里指出去查系数，不静默截断。
- **校准**：拿功率计实测，改 `%APPDATA%\CORE-BUSY\settings.json` 里的五个分项系数
  （`SystemPowerCalibration` / `BoardWatts` / `FanWatts` / `GpuFallbackWatts` / `DramWattsPerGb`）
  即可，无需重新编译；越界或非有限值一律**回落默认值**而非截断。
- **已知局限**：不含显示器与 VRM 转换损耗；同型号非公版显卡可有 ±20% 偏差；笔记本独显的 TGP 按
  0.6 折算（OEM 可在 35–150 W 间自由配置）；多卡时副卡共用主卡的负载比例；混合介质机器上摆幅
  只取摆幅最大的那一种介质。各项系数均为公开规格值，**目的是量级正确，不是精确**。

## 核心健康度评分

每核 0–100 = 频率达成 60% + 热裕度 25% + 时钟稳定 15%，缺项按剩余权重归一化；WHEA 已纠正错误作用于总分。

| 分量 | 权重 | 口径 | 读不到时 |
| --- | --- | --- | --- |
| A · 频率达成度 | 60% | 该核**有效频率**峰值 ÷ 同封装各核峰值中位数（允许 5% 自由带） | 证据帧 / 参照不足 → 三项一并不给分 |
| B · 热裕度 | 25% | 封装温度距 95 ℃ 的余量；70 ℃ 以内不扣分，全核共担 | 缺席，权重由剩余分量归一化 |
| C · 时钟稳定性 | 15% | 满载窗口内频率的鲁棒变异系数（MAD） | — |
| WHEA | 作用于总分 | 近 7 天每条 −5、封顶 −25；存在未纠正错误则总分封顶 60 | 读不到与「读到 0 条」严格区分 |

- 判分频率用 LHM 的逐核**有效频率**（硬件驻留加权的时间平均）。**P-state 档位时钟不能判分** ——
  它是离散档位、与负载无关，8 颗核读到同一个值会让比值恒 1、人人满分（仍用于 Tile 频率显示）。
- **证据判据**：OS 使用率 ≥ 70% **或** 硬件活跃度 ≥ 70%，累计 ≥ 3 帧即评分；样本不足一律显示 `-`。
- **参照有效性闸**：达标核 < `max(3, ⌈n/2⌉)` 时全体不给分 —— 中位数在 1–2 个点时会退化成
  「某一颗核自己」→ 比值恒 1 → 假 100。`-` 是诚实的「没有证据」，`100` 不是。
- 分档：≥ 90 良好 / 80–89 正常 / 70–79 需关注 / < 70 异常。
- 逐核电压与历史基线**只展示、不计分**：前者缺一个标定过的同频点，后者的估计量自带约 2.5% 系统性偏差。
- 它是**合成代理指标**，不是厂商认证的「损耗百分比」—— CPU 没有可读的健康度寄存器。

「自检」结果写入 `core-selftest.json`：首次通过时记下校验和作为期望值，之后每次与之比对，
**跨运行的不一致本身就是故障信号**。方法论借鉴 Prime95 / mprime，不使用其代码或二进制。

## 主题

| 主题 | 触发 | 说明 |
| --- | --- | --- |
| Intel Blue | CPU 为 Intel，或手动锁定 | 深蓝基底，热力图 深蓝→蓝→青→浅青 |
| AMD Red | CPU 为 AMD，或手动锁定 | 近黑基底，热力图 黑→暗红→红→橙 |
| Neutral | 厂商未知 | 中性石墨基底，低饱和蓝强调 |

设置中可选「自动 / Intel Blue / AMD Red」，默认跟随 CPU 厂商。三套主题共用同一中性深灰基底
（`#1A1A1A` → `#232323` → `#2B2B2B`，靠明度分层而非透明度），唯一差异是强调色。
高负载（≥ 80%）在三种主题下统一用红色。**CPU 身份徽章始终反映真实厂商，不随主题变化**。
主题与核心分区在窗口构建前生效，改动后需重启（主窗口会提示并可一键重启）。

| 主题 | 自动 / Intel Blue / AMD Red（需重启） |

## 数据文件

数据在 `%APPDATA%\CORE-BUSY\`（标题栏「更多」按钮可直接打开该目录）：

| 文件 | 内容 |
| --- | --- |
| `settings.json` | 用户配置 |
| `energy-history.json` | 每日累计焦耳与观测秒数 + 账本口径标识（能耗日历的数据源） |
| `energy-history.{口径}.json` | 口径变更时自动归档的旧账本，只增不改 |
| `core-health.json` | 每核历史最好「站位」（只展示，不计分） |
| `core-voltage.json` | 逐核电压采样（只展示，不计分） |
| `core-selftest.json` | 逐核自检校验和（跨运行比对） |

## 项目结构

```text
src/
├── CoreBusy.App      # WPF 主程序（UI / ViewModel / 托盘 / 主题 / Mock 回退）
├── CoreBusy.Core     # 领域模型与接口（ICpuMonitorService、CoreStatusClassifier）
├── CoreBusy.Windows  # 真实采集（CPU 拓扑 / 性能计数器 / WMI / 电源策略）
└── CoreBusy.Sensor   # 硬件传感器（LibreHardwareMonitor）
scripts/              # 构建与静态检查脚本
docs/                 # 各版本截图
```

`ICpuMonitorService`（`GetCpuInfo / GetSnapshot / GetCoreSnapshots`）是 UI 与硬件采集的唯一边界：
`WindowsCpuMonitorService` 为默认注入，`MockCpuMonitorService` 作为回退，UI 无感知。
真实服务在后台线程按采样周期采样，UI 定时器读取最新快照，两端解耦。
